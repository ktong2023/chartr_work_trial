# Clinic CLI

`clinic patients` lists the complete cohort: `{complete, evaluation_time, patients}`.
Each patient entry has a Patient resource and its EpisodeOfCare resources.
`clinic records PATIENT_ID` returns `{complete: true, resources: [...]}`: every available
record for that patient in event-time order, including full notes and orders. There is
no pagination.
`clinic reviews [--patient PATIENT_ID]` returns `{complete: true, items: [...]}` including
resolved items. Empty items is a successful empty result, not a retrieval error.

Command templates below use placeholders, not executable patient records.
Substitute `PATIENT_ID`, `EPISODE_ID`, `RECORD_ID`, and `ITEM_ID` with IDs returned
by the clinic tools. Substitute `REASON_CODE` and `WORKFLOW_STATUS` with the allowed
values supported by your review, and replace `EXPLANATION_TEXT` with your explanation.
Square brackets around `--patient PATIENT_ID` above indicate an optional argument.

```sh
clinic create --json '{"patient":"PATIENT_ID","episode":"EPISODE_ID","category":"treatment_review","reason":"REASON_CODE","destination":"clinical_review","status":"WORKFLOW_STATUS","evidence":["RECORD_ID"],"explanation":"EXPLANATION_TEXT"}'
clinic update ITEM_ID --json '{"status":"WORKFLOW_STATUS","evidence":["RECORD_ID"],"explanation":"EXPLANATION_TEXT"}'
```

Create requires exactly all eight keys shown. Update accepts only `status`,
`evidence`, `explanation`; at least one is required and omitted fields are retained.
Patient, episode, ID, original creation, category, reason and destination cannot
be changed. Both operations return the persisted FHIR Task resource directly.
New IDs are generated by the service. Writes are atomic and immediately readable.

Allowed reasons: `UNRESOLVED_TREATMENT_CONCERN`, `CONFLICTING_ACTIVE_PLANS`.
Allowed workflow statuses: `open`, `needs_clarification`, `resolved`.
Only category `treatment_review` and destination `clinical_review` are supported.
`evidence` is a nonempty JSON array of up to 20 clinical record IDs in the item's
patient and episode. Explanation must be nonempty and at most 4,000 characters.
Request bodies are limited to 16 KiB. Ordering and repeated citations have no meaning.

Clinical sources are immutable. There are no delete, reset, admin, export, grading,
or raw database operations.
Exit 0 means success, exit 2 means invalid arguments/operational validation, exit 3
means a transport/service fault. Errors go to stderr as JSON or a transport message.
Writes are never retried automatically: if the response is lost, inspect the queue
before deciding whether to retry. An unknown patient is an error, not an empty chart.

# Limited FHIR R4 JSON

This is a small clinic API carrying FHIR R4 (4.0.1) resources, not a conformant FHIR
REST API. The service validates resource structure against the pinned HL7 R4 JSON
schema. It does not implement full profile, terminology, or FHIRPath validation.

Patients use Patient; care episodes use EpisodeOfCare. Notes, messages and
administrative records use DocumentReference: `description` is the full readable text, also encoded
as UTF-8/base64 in `content.attachment.data`. `date` is documentation time;
`event-time` is applicability time. `author` identifies the note's author; the
`author-role` extension states their role.

Orders use MedicationRequest; `authoredOn` remains the original order time.
Custom order extensions: `cancelled-at`, `cancelled-by`, `replaced-by`.
Laboratory requests use ServiceRequest; `note` carries free-text order notes.

Review items use Task: `for` is the Patient, `focus` is the EpisodeOfCare, `code`
is the category, `reasonCode` the reason, `owner: Organization/clinical-review`
maps to destination `clinical_review`, `description` is the explanation, and
`input[].valueReference` holds typed evidence references. Every clinical source and
review item carries an `episode` extension. Extension URLs are under
`https://chartr.example/fhir/StructureDefinition/`; custom code systems are under
`https://chartr.example/fhir/CodeSystem/`. These are local definitions, not HL7 codes.

| Clinic businessStatus | R4 Task.status | Meaning |
| --- | --- | --- |
| open | requested | Review requested for an unresolved concern |
| needs_clarification | requested | Review requested for incompatible instructions |
| resolved | completed | This specific review concern has been addressed |

The clinic status is the code in `businessStatus`, never an invented Task.status.
`authoredOn` is preserved on update; `lastModified` uses the fixed evaluation time.
The `event-sequence` extension orders workflow changes at that simulated time.
Real execution time is separate from clinical time.
