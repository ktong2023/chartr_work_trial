# Clinic CLI

`clinic patients` lists the current cohort: `{complete, evaluation_time, patients}`. Each entry has
a Patient resource and its EpisodeOfCare.
`clinic records PATIENT_ID` returns `{complete: true, resources: [...]}`: every record in that
patient's chart in event-time order. It works for current-cohort patients and for the patients in
`clinic history`. There is no pagination.
`clinic history` returns `{complete: true, determinations: [...]}`: determinations the clinic's
reviewers already made for other patients, as of the same evaluation time. They are read-only.
`clinic determinations [--patient PATIENT_ID]` returns the determinations recorded so far for the
current cohort.

Command templates below use placeholders. Substitute IDs returned by the clinic tools, allowed
values, and your explanation; `null` is valid JSON where a field allows it.

```sh
clinic determine --json '{"patient":"PATIENT_ID","status":"STATUS","plan":"RECORD_ID","due_date":"YYYY-MM-DD","completion":"RECORD_ID","explanation":"EXPLANATION_TEXT"}'
clinic redetermine DETERMINATION_ID --json '{"status":"STATUS","due_date":null}'
```

`determine` requires exactly the six keys shown and returns the saved determination. `redetermine`
accepts any of `status`, `plan`, `due_date`, `completion`, `explanation` (at least one); omitted
fields keep their saved values. The patient of a determination cannot be changed. New IDs are
generated by the service. Writes are atomic and immediately readable, and are never retried
automatically: if a response is lost, inspect `clinic determinations` before retrying.

Fields:

| Field | Value |
| --- | --- |
| `status` | `no_requirement`, `not_due`, `overdue`, `completed`, or `unclear` |
| `plan` | ID of the follow-up plan record in force for the requirement, or `null` |
| `due_date` | Due date of the requirement in force (`YYYY-MM-DD`), or `null` |
| `completion` | ID of the record that completes the requirement, or `null` |
| `explanation` | Nonempty text, at most 4,000 characters; its only allowed whitespace characters are space, tab, carriage return and line feed |

Statuses: `no_requirement` means no follow-up requirement is in force; `not_due`, the requirement
in force is not yet due; `overdue`, it is past its due date and has not been completed;
`completed`, it has been completed; `unclear`, its due date cannot be determined from the current
documentation. Record IDs may be given bare (`RECORD_ID`) or typed (`ServiceRequest/RECORD_ID`).
`plan` must be a follow-up plan record (ServiceRequest with `intent: plan`); `plan` and
`completion` must belong to the patient's chart.

Exit 0 means success, exit 2 means invalid arguments or validation, exit 3 means a transport or
service fault. Errors go to stderr. There are no delete, reset, admin, export, or grading operations.

# Limited FHIR R4 JSON

A small clinic API carrying FHIR R4 (4.0.1) resources, not a conformant FHIR REST API. Resource
structure is validated against the pinned HL7 R4 JSON schema.

Patients use Patient; care episodes use EpisodeOfCare. Notes, messages, scanned documents and
administrative records use DocumentReference: `description` is the full readable text, also
encoded as UTF-8/base64 in `content.attachment.data`; `date` is documentation time; `author`
identifies the author. Every clinical record carries `episode`, `event-time` (applicability time)
and `author-role` extensions.

Medication orders use MedicationRequest (`authoredOn` is the order time, `requester` the
prescriber). Doses given in clinic use MedicationAdministration (`effectiveDateTime` is when the
dose was given; `request` links its order). ServiceRequest with `intent: order` requests a service
such as a laboratory test; ServiceRequest with `intent: plan` is a follow-up plan; for both,
`authoredOn` is documentation time, `requester` names the author and `note` carries free text.
Results use Observation (`effectiveDateTime` is collection time, `issued` is result time,
`basedOn` links the order). Visits use Encounter (`status` is `planned` or `finished`;
`period.start` is the visit time).

Determinations use Task: `for` is the Patient, `focus` the EpisodeOfCare, `businessStatus` the
status, `input` entries typed `governing-plan` and `completion` hold the plan and completion
references, the `due-date` extension holds the due date, and `description` the explanation.
Extension URLs are under `https://chartr.example/fhir/StructureDefinition/`; code systems under
`https://chartr.example/fhir/CodeSystem/`. These are local definitions, not HL7 codes.
