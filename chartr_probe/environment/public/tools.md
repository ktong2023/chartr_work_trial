# Clinic CLI

`clinic patients` returns `{complete, evaluation_time, patients}`. Each entry contains `patient`, all `episodes`, and a `target_episode` ID specifying the assignment's scope.
`clinic records PATIENT_ID` returns `{complete: true, resources: [...]}` containing the whole patient chart in event-time order, including other episodes. There is no pagination.
`clinic determinations [--patient PATIENT_ID]` lists saved determinations.

Templates use placeholders, not actual records. Substitute IDs returned by the tools and conclusions established by your review:

```sh
clinic determine --json '{"patient":"PATIENT_ID","episode":"EPISODE_ID","status":"STATUS","plan":"PLAN_ID","course":"COURSE_ID","doses":["ADMINISTRATION_ID"],"completion_date":"YYYY-MM-DD","due_date":"YYYY-MM-DD","result":null,"explanation":"EXPLANATION_TEXT"}'
clinic redetermine DETERMINATION_ID --json '{"result":"RESULT_ID","status":"completed"}'
```

Create requires exactly the ten keys shown. Update accepts any nonempty subset except patient and episode. Omitted fields are retained. Patient and episode are immutable. IDs are generated by the service; writes return the saved FHIR Task directly. Writes are atomic and never automatically retried; inspect saved state after a lost response. Duplicate determinations are permitted operationally but do not satisfy the assignment.

`status`: `no_requirement`, `not_due`, `overdue`, `completed`, or `unclear` as defined by policy.
`plan`, `course`, `result`: the source record ID or JSON null. Typed IDs such as `Observation/RECORD_ID` are also accepted.
`doses`: an array of up to 40 MedicationAdministration IDs. Order is not graded; identify exactly the policy's counted sequence. Other episodes' records can be cited if they belong to this patient.
Dates are ISO `YYYY-MM-DD` or null. Explanation is nonempty text, at most 4,000 characters; R4 whitespace permits space, tab, CR and LF. Requests are limited to 16 KiB. Exit 0 is success, 2 is invalid arguments or operational validation, 3 is transport/service failure. There are no admin, reset, export, history, delete, or grading operations. Sources are immutable.

# Limited FHIR R4 representation

Resources are validated against the pinned R4 4.0.1 structural schema, not full FHIR REST/profile/terminology conformance.
- Patient and EpisodeOfCare identify the chart and episodes.
- MedicationRequest identifies a course and its episode; `dosageInstruction` is source text.
- MedicationAdministration uses `effectiveDateTime`, `status`, and `request` (course).
- ServiceRequest with `intent: plan` uses `note` for the interval and `supportingInfo` for its course. A local `replaces` extension points to a prior plan where present.
- Observation uses `effectiveDateTime` (specimen date), `issued`, `status`, `code`, and `basedOn` (course).
- DocumentReference uses `description` for full readable text, identically encoded as base64 in its attachment. Its `date` is documentation time. `author-role` identifies amendment authority.
- Clinical resources have original `episode` and `event-time` extensions. The policy defines how amendments affect their interpretation.
- Saved Task: `for` is patient, `focus` is target episode, `businessStatus` holds status. Typed inputs `plan`, `course`, `dose`, and `result` hold references; `completion-date` and `due-date` extensions hold dates. `description` is the explanation. Task.status is always `completed` because the determination was recorded, irrespective of its businessStatus.

Local extension and code-system URLs begin `https://chartr.example/fhir/`. These local definitions do not add new HL7 standard status values.
